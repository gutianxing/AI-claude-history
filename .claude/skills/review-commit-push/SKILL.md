# Review-Commit-Push 工作流

自动化代码审查、提交和推送流程。

## 触发条件

- 用户请求"提交代码"或"帮我提交"
- 用户说"review 后提交"、"审查后推送"
- 用户要求"提交并推送"
- 用户想要完成代码变更的完整提交流程

## 工作流程

### 第一步：检查当前状态

1. 运行 `git status` 查看变更文件
2. 运行 `git diff --stat` 查看变更统计
3. 运行 `git log --oneline -5` 了解最近提交风格

### 第二步：代码审查

对每个变更文件进行审查：

1. **功能正确性** - 逻辑是否正确，是否满足需求
2. **代码质量** - 命名规范、代码结构、可读性
3. **潜在问题** - 安全风险、性能问题、边界情况
4. **最佳实践** - 是否符合项目编码规范

审查输出格式：
```
## 审查结果

### 文件: <filename>
- ✅ <优点1>
- ⚠️ <警告/建议>
- ❌ <必须修复的问题> (如果有)

### 总体评价
<简要总结>
```

### 第三步：确认提交

向用户展示：
1. 变更文件列表
2. 审查摘要
3. 拟定的提交信息

询问用户是否确认提交。如果用户有修改意见，调整后再确认。

### 第四步：执行提交

```bash
git add <files>
git commit -m "<commit-message>"
```

提交信息格式：
```
<type>(<scope>): <description>

[optional body]

Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>
```

类型 (type):
- `feat`: 新功能
- `fix`: 修复 bug
- `refactor`: 重构
- `docs`: 文档更新
- `style`: 代码格式
- `test`: 测试
- `chore`: 构建/工具

### 第五步：推送到远程

```bash
git push
```

如果是首次推送新分支：
```bash
git push -u origin <branch-name>
```

### 第六步：确认完成

显示推送结果，包括：
- 提交哈希
- 推送的分支
- 远程仓库 URL

## 错误处理

- **没有变更**: 提示用户当前没有需要提交的变更
- **推送失败**: 显示错误信息，询问用户是否需要重试或处理冲突
- **审查发现严重问题**: 阻止提交，要求用户先修复问题

## 注意事项

1. 只暂存用户确认的文件，不自动添加所有文件
2. 提交信息要简洁明了，描述"做了什么"而非"怎么做的"
3. 如果变更敏感（删除文件、修改配置等），额外提醒用户确认
4. 尊重用户的 .gitignore 和 pre-commit hooks
